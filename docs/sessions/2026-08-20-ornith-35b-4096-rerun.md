# 2026-08-20 — Ornith-1.5-35B agentic remeasure @ 4096 floor

## Goal
Remeasure `Ornith-1.5-35B-Q4_K_M.gguf` agentic-full under the 4096-token floor (queued in `models/TASK.md`; the 4 web_research fails were cap-truncation suspects). Verify the observability stack end-to-end on a real MoE run.

## Hardware
- Discrete 8 GB-class NVIDIA, Baseline `VRAM_LIMIT_MB = 8000`, MoE target (`--n-cpu-moe 41` auto, experts to CPU).
- Engine: `llama.cpp-releases/upstream/b10375` (CUDA build), run env `AUTORESEARCH_SKIP_FREE_CLAMP=1` + `AUTORESEARCH_PHYSICAL_VRAM_KEEPOUT_MB=512` (MoE keepout).

## Setup
- Baseline: `MODEL='Ornith-1.5-35B-Q4_K_M.gguf'`, `NO_MMAP=False` (mmap, 21.7 GB file), `CTX_SIZE=65536`, `KV q4_0`, batch 256/128, threads 6/8, `N_GPU_LAYERS=99`, `REASONING_PRESERVE=True`, sampler TEMP 0.6 / TOP_P 0.95 / TOP_K 20.
- Harness: agentic `max_tokens` floor 4096 + 420 s turn timeout (commit `df57de4`), rotated logs + sidecars (commit `76dc8aa`).

## Commands
- `AUTORESEARCH_SKIP_FREE_CLAMP=1 AUTORESEARCH_PHYSICAL_VRAM_KEEPOUT_MB=512 ./venv/Scripts/python.exe benchmark_search.py --agentic-full --no-coding --desc "trial Ornith-1.5-35B-Q4_K_M.gguf agentic rerun (max_tokens 4096)"` (no timeout).

- **0.7333 → 0.8667 (13/15)**; row `f8980537` `on_front`, bench_tg 27.8, peak VRAM 3.6 GB. Run wall ~102 min (quick 519 s + full 5540 s).
- **Recovered (were 4/15 web_research fails):** T046 **1.00** (43 calls, len 9816), T048 **1.00** (45 calls, len 11662), T050 **1.00** (29 calls, len 11626). T044 also 1.00 (len 10426). The 4096 floor fixed the truncation-starved research reports.
- **T053 (0.00) = 65k ctx ceiling, proven with direct evidence:** HTTP 400 body captured verbatim — `{"error":{"code":400,"message":"request (124983 tokens) exceeds the available context size (65536 tokens)","type":"exceed_context_size_error","n_prompt_tokens":124983,"n_ctx":65536}}`. Server log shows one `truncated = 1` (n_tokens 65535) before it. Suspect: accumulated history + `REASONING_PRESERVE` think re-renders inflate the request past 65k.
- **T054 (0.00) = content failure, not truncation:** 29 calls, report len=7173 (above floors), no yearly-value keywords. Same family-wide retrieval-path weakness as both 9B generations.
- **No max_tokens cap hits:** 0 turns decoded to 4096 in the run log. 5 `length_stops` flags fired (T008/T046/T048/T050/T054) — all `</s>`-stop-string stops, confirming the metric over-counts (caveat updated; print relabeled).

## Errors
- One `truncated = 1` (65k ctx) + one HTTP 400 `exceed_context_size_error` on T053 — both captured and preserved by the rotated log + HTTP-body observability (the exact evidence class the harness used to lose).
- `length_stops` metric noise: 5 flags / 0 real cap hits (see Findings).

## Decisions
- Keep the capability floor at 4096; T053's ceiling hit is a context-budget question, NOT a token-cap one. Candidate A/B: ctx 131072, or `REASONING_PRESERVE` off to shrink request size (it re-renders think traces into every prompt).
- Metric print relabeled: "stop-string stop or cap hit — confirm n_decoded in server log" (the tool-call exclusion from 2026-08-19 was insufficient).
- 35B card/README/family table updated; TASK.md ticked. Baseline left seeded to the 35B.
