Guardrails — Allow, Deny e Hooks

Na prática o agente vira uma fila de tools: ler arquivo, editar, terminal. Guardrail é o segurança da boate — lista da casa, checagem na porta, comanda na saída. Sem isso, cada comando vira “Permitir?” e logo você só aperta Enter. Mesma ideia no Cursor e no Claude Code.

← Dia 2 Guia Glossário

Resultado:
Configurar Allow/Deny e hooks pré/pós no Cursor e no Claude Code; abrir o Claude só com as tools que você quer.

Duração:
35–50 minutos (conceito + simulador + um teste real).

Pré-requisito:
Cursor e/ou Claude Code. Semana 2 · Dia 2 (MCP) ajuda, mas não é obrigatório.

1. A boate do agente

O agente não fica só digitando texto. Ele chama tools: abrir arquivo, editar, rodar comando, usar MCP. Isso acelera o trabalho — e também pode apagar pasta, vazar .env ou instalar coisa errada.

Sem guardrail, o harness fica perguntando “Permitir?” o tempo todo. No começo você lê. Depois cansa e aperta Enter. Isso tem nome: fadiga de aprovação.

Com guardrail, a regra vem antes. Allow = passa sem perguntar. Deny = nem tenta. Pre-hook = ainda dá para barrar na porta. Post-hook = depois que já rodou, só anota (não desfaz o que aconteceu).

BoateAgente
Quem está na fila Tool querendo rodar
Lista da casa Deny / Allow
Checagem na porta Pre-hook
“Posso entrar?” Ask (o harness pede confirmação)
Comanda na saída Post-hook

Na prática

  • Comandos seguros (git status, ler src/) podem entrar sozinhos (Allow). O perigoso continua pedindo confirmação — ou fica de fora (Deny / Pre-hook).
  • Escrever no chat “não leia o .env” o modelo pode ignorar. Deny ou hook o harness aplica.
  • Se o Pre-hook sair com código 2, o erro volta pro agente e ele pode mudar o plano (ex.: “npm bloqueado, use bun”).
  • Lista no repo (settings.json, hooks) = todo mundo no clone usa a mesma regra.
  • No Windows a caixa de areia (sandbox) é fraca ou inexistente no Claude; no Cursor sem WSL2 quase não protege arquivo. Guardrail continua valendo.
  • Post-hook deixa rastro do que passou — ajuda a ajustar a lista depois.

Passo a passo na porta

  1. O agente pede algo (ex.: rodar um comando).
  2. Deny: se estiver bloqueado, para. Não roda.
  3. Pre-hook: se existir script, ele inspeciona. Pode barrar e devolver erro.
  4. Allow → roda sem perguntar. Senão → Ask (pede confirmação).
  5. A tool roda.
  6. Post-hook: se existir, só registra ou avisa — já aconteceu.

No Claude Code a ordem é deny → ask → allow: a primeira regra que bater decide. Não é pedido no chat; é regra do harness. Fonte: Configure permissions.

2. Sandbox — a caixa de areia

Sandbox em inglês é a caixa de areia do parquinho: brinca dentro; fora da borda, acabou. No agente, a “borda” é o sistema operacional (arquivos e rede). Em geral o projeto fica dentro. Chaves SSH, pastas do sistema, domínio que você não liberou — ficam fora, e o SO pode bloquear.

No Windows a história muda conforme o harness:

Claude CodeCursor
macOS Sim — Seatbelt; /sandbox, modo auto-allow Sim — Seatbelt
Linux Sim — Bubblewrap (+ socat) Sim — Landlock + seccomp (kernel recente)
Windows No Windows puro, não. Precisa rodar o Claude no WSL2. Com WSL2 fica perto do Linux. Sem WSL2, quase não protege arquivo — no máximo mexe um pouco na rede.

No Windows, no dia a dia, foque em guardrail (Allow / Deny / hooks) — com ou sem sandbox.

Fontes: Claude — sandboxed Bash · Cursor — Run modes · Cursor — agent sandboxing.

3. Allow e Deny — a lista da casa

RegraEfeito
Allow (permitir) Essa tool / padrão roda sem perguntar de novo.
Deny (negar) Bloqueia. Só o nome da tool (ex. Bash) pode tirar a tool da sessão; com padrão (ex. Bash(rm *)) barra só o que combina.
Ask (perguntar) Sempre pede confirmação para aquele padrão (Claude Code).

Claude Code

Arquivo: .claude/settings.json (projeto) ou ~/.claude/settings.json (usuário).
UI: comando /permissions. 

{
  "permissions": {
    "allow": ["Bash(git status *)", "Read"],
    "deny": ["Read(.env)", "Read(.env.*)", "Bash(rm *)"]
  }
}

Docs: Configure permissions, Settings.

Cursor

IDE: lista de comandos/MCP permitidos em .cursor/permissions.json (e Settings → Agents → Run Mode).
CLI do Cursor: allow/deny em .cursor/cli.json / ~/.cursor/cli-config.json. 

{
  "permissions": {
    "allow": ["Shell(git)", "Shell(npm)"],
    "deny": ["Shell(rm)", "Read(.env*)"]
  }
}

Docs: permissions.json, CLI permissions.

4. Hooks — porta e saída

Allow e Deny são a lista. Hook é script: dá para decidir com lógica (olhar o comando, o caminho do arquivo…).

  • Pre-tool — antes de rodar. Pode bloquear. Claude: PreToolUse. Cursor: preToolUse (shell também tem beforeShellExecution).
  • Post-tool — depois que já rodou. Serve para registrar ou avisar. Claude: PostToolUse. Cursor: postToolUse. Não desfaz o que a tool fez.

Claude Code — PreToolUse

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "powershell.exe -File scripts/hooks/check.ps1"
      }]
    }]
  }
}

Script lê JSON no stdin; pode devolver permissionDecision: "deny" ou sair com código 2 para bloquear. Fonte: Hooks.

Cursor — preToolUse

{
  "version": 1,
  "hooks": {
    "preToolUse": [{
      "command": ".cursor/hooks/check.ps1",
      "matcher": "Shell|Write"
    }],
    "postToolUse": [{
      "command": ".cursor/hooks/audit.ps1"
    }]
  }
}

Arquivo: .cursor/hooks.json. Saída JSON com permission: "deny" (ou exit 2). Fonte: Cursor Hooks.

Exemplo neste repositório

Aqui no workshop já existem dois scripts em scripts/hooks/:

  • block-adhoc-eval.ps1 — barra Python/comandos fora da lista (script solto, flag de teste na linha de comando em vez de editar o config.py…).
  • block-gate-tamper.ps1 — impede o agente de mexer nos arquivos de segurança (hooks e settings).

No Claude Code: .claude/settings.json (Deny + Pre-hook). No Cursor: .cursor/hooks.json, se o projeto trouxer esses arquivos.

5. Abrir o Claude só com as tools que você quer

Três flags. Não são a mesma coisa. Olhe no claude --help:

FlagO que faz
--tools Lista da sessão: só essas tools do Claude existem nesta sessão. "" = nenhuma. Ex.: só ler e editar.
--allowedTools Sem perguntar: essas rodam sem prompt (as outras tools continuam existindo).
--disallowedTools Deny na CLI: só o nome (ex. Edit) remove a tool; com padrão (Bash(rm *)) bloqueia só o que combina. 
# Só leitura + edição (sem Bash na sessão)
claude --tools "Read,Edit"

# Bash existe, mas git push fica negado; git status passa sem perguntar
claude --allowedTools "Bash(git status *)" --disallowedTools "Bash(git push *)"

# Sem tools do Claude (só texto)
claude --tools ""

--tools não corta MCP. Para negar MCP: --disallowedTools "mcp__*" (ou carregar MCP só via --mcp-config + --strict-mcp-config). Referência: CLI reference.

6. Simulador

Marque Deny, Allow, Pre-hook e Post-hook e veja o que acontece com quatro pedidos.

Ativo agora

    Prática

    No simulador

    1. Nada marcado → tudo pede OK.
    2. Só Deny → .env e rm bloqueados.
    3. Deny + Allow + Pre-hook → o seguro passa; o perigoso para na lista ou no hook.
    4. Com Post-hook: ele não impede — só age depois.

    No Cursor ou no Claude Code (escolha uma)

    1. Claude Code: /permissions — coloque Deny em Read(.env) e peça para ler o .env.
    2. Claude CLI: claude --tools "Read,Edit" — confira se Bash some da sessão.
    3. Cursor: Settings → Agents → Run Mode / lista de permitidos, ou abra .cursor/hooks.json / permissions.json se o projeto tiver esses arquivos.
